### sala --help (exit 0)
salamander — the operator for Claude Code across your machines (fleet: versions, heartbeat,
remote /provision) and, on the box that hosts them, named long-lived sessions in tmux that survive reboots
and CLI updates, resumed by transcript UUID, reachable from Remote Control.

  salamander spawn  [NAME] [--mandate FILE|TEXT [--no-confirm]] [--cwd DIR] [--lane L] [--model M] [--effort E] [--fork UUID] [--dry-run]
                                     (--brief FILE and --prompt TEXT: the mandate's older names, kept as aliases; --lane L records the lane too (--model fable is refused on any lane but Ultra, subscription-1); a bare spawn from a Claude session records it on the throwaway's row, spawned_by: that session may later retire it with no words; every bare spawn also writes the throwaway tag, throwaway=1, on the row: any session may retire a tagged row with no words, between turns)
                                     (--fork UUID is a resume: like a recycle or revive it passes the user settings' permissions.defaultMode as --permission-mode)
  salamander spawn  NAME --project <page key> --role front|back|none [--surface sala|slack] [--mandate FILE|TEXT] [--lane L] [--model M] [--effort E] [--cwd DIR] [--dry-run]
                                     --role none: a session to work with, named after the project and on no agents map: nothing is registered with stackshot and its row carries no role, a name the record lists is refused, no mandate is required, and it starts in $HOME (the front rules), never in SALA_BACK_CWD; the sessions list shows it as it shows a front agent (left list, unread count, search).
                                     Otherwise a project agent's session (lib/spawn.sh): the name must be registered with stackshot (on the project's agents map) first —
                                     not there: exit 3 and `REGISTER: <key>` + stackshot's `post project-agent` command to run (with --role and --mandate the spawn registers it itself); stackshot's
                                     project record not fresh enough to answer: exit 6 and no pane (retry when it is fresh, or SALA_AGENT_CHECK=off); a back agent needs a mandate and starts on it unasked, in the directory SALA_BACK_CWD names (refused when this machine lacks it), else in $HOME when it is unset (--cwd wins);
                                     --surface slack (front only) is a front agent that answers the owner's Slack app messages: it starts in the directory SALA_SLACK_CWD names (refused when that key is unset or the directory is missing; --cwd wins) and its row carries surface: slack; SALA_SPAWN_REGISTER runs after
  salamander spawn  --suggest-name --project <page key> --role front|back|none [--prefix P] [--new]   a free name, never a taken one: <prefix>-main only for a
                                     front agent of a project with no agent yet (the record says so, or --new: no page yet), else <prefix>-<random word>;
                                     the prefix is --prefix, else the project record's, else the page-name convention (<scope>-<slug>, the scopes SALA_SCOPES)
  salamander spawn  NAME --side (--fork-of AGENT | --project <page key> --item board#N) [--item board#N] [--agents A,B] [--mandate FILE|TEXT] [--lane L] [--model M] [--effort E] [--cwd DIR] [--dry-run]
                                     a side conversation (lib/spawn.sh, docs/side-sessions.md): a short-lived session started in one step, on no
                                     agents map, named <agent or project prefix>-side-<word><nn>: a fork of a running agent's conversation, or a fresh
                                     session scoped to an item's project page that reads the item and the involved agents' transcript excerpts;
                                     no quiet watch, no auto-retire, no cap — it retires only on the owner's word, and only once `side done` ran
  salamander spawn  --suggest-name --side (--fork-of AGENT | --project <page key>)   the side session's name (<prefix>-side-<word><nn>)
  salamander spawn  --list
  salamander recycle [--update] [--force]   relaunch every pane, this one included, from one detached driver
                                     (a Claude session's pane queues it with `sala op recycle`)
                                     (--update: `claude update` first — the two halves of "recycle")
                                     (--force: every idle pane, not only stale-binary ones — also reloads CLAUDE.md/settings)
                                     (a pane held busy for SALA_PAUSE_AFTER s, default 900, has its turn interrupted with one Escape and is relaunched with a note of what it was doing; SALA_PAUSE_SCOPE=background|all|off (default background: back agents only, a front agent is never paused), 0 = wait as before; a pause that does not take is tried again every SALA_PAUSE_RETRY s, default 120; no pause once the relaunch has waited past SALA_HOLD_MAX)
                                     (every relaunch — recycle, revive, unpark, restore — passes the user settings' permissions.defaultMode as --permission-mode, because a resumed session otherwise keeps the mode its transcript recorded)
  salamander recycle --when-idle [--from NAME] [--change REF] "<reason>" | --list | --cancel [ID]   any session: ask for a recycle; it
                                     only records the request — `watch` runs the recycle at its next run, each busy pane once idle (lib/recycle-request.sh); --change REF (a commit sha or pr<N>) holds it until that change is in the checkout
  salamander revive [--dry-run] [--force] [--only NAME] [--lane-default] [--rescue] | --save-map | --map-history | --self [--dry-run] [--rescue]
                                     (--rescue, with --only or --self: a stale background-task row — the exit dialog, the Stop hook's record or the
                                     mod listing work while no child process runs under the claude — no longer holds the pane)
                                     (a claude still running SALA_EXIT_WAIT s after its /exit — a hung process — is ended by its pid, SIGTERM then SIGKILL, and its session
                                     resumed: the dry run says "will end a stuck process"; never the session running the command; SALA_EXIT_END=0: never)
  salamander revive --only NAME --cwd DIR [--force] [--dry-run]   move one session: relaunched in DIR, which its pane-map row then records (a session queues it, the owner's words only: op revive)
                                     (SALA_BACK_CWD naming a directory: every wake and relaunch of a project's back agent (revive, recycle, lane and model moves,
                                     restore, unpark) starts there and its pane-map row follows; --cwd wins; every other session keeps its folder; an sdk-lane pane
                                     resuming in place after an API credit refusal does not ask: it stays in its folder until the next relaunch)
  salamander rc     [--ensure|--start|--status|--restart|--stop|--archive ID…|--titles [--dry-run|--apply (--only NAME (repeatable)|--all)]]   (the Remote Control server; retired; --titles: claude.ai session titles)
  salamander map    [--write PATH]
  salamander update [HOST…|--fleet] [--check]   CLI update: here (= recycle --update --force), named hosts over ssh, or the whole fleet then here
  salamander provision [--check] [HOST…]  the spec's script steps on every box (the others in parallel, this box last, then a recycle); HOST… = just those, no recycle
  salamander provision --only STEP[,STEP…] [--check] [HOST…]   just those steps on every box (or HOST…): the apply, then their check; no CLI update, no recycle
  salamander provision --settle <set> <host> <step> ok|gave ["<note>"] · --waiting <set> <host> <step> "<text>" · --sets   a provision set's leftovers
  salamander retire <tmux-session>|--id <conversation-id> [--keep-web] [--busy] [--skip-writeup] [--self] [--leave-items] [--dry-run]
                                     end a Claude session for good (exit · kill · unmap · snapshot · archive); the exact tmux session name, or --id for a session known by its conversation; --self ends the session the command runs in (queue it: sala op retire NAME --self; its own running turn is not counted busy); --force is gone
  salamander close-shell <tmux-session> [--busy] [--dry-run]   close a session whose panes run no Claude (kill · unmap · snapshot)
  salamander forget-row <name> [--dry-run]   drop a pane-map row whose tmux session is gone (and its lane and model rows)
  salamander rename OLD NEW [--dry-run]           rename a live pane end to end (/rename · tmux · map · notes · heartbeat; a sleeping session without waking it, its tmux session gone or not; renames OLD's entry on its project's page via stackshot if the page does not list NEW)
  salamander sessions [--all] [--full] [--json] | --check [--dry-run] | --migrate [--dry-run]   the session registry (phases 1 and 2; docs/session-registry.md):
                                     one row per session with an id that outlives a rename; read-only listing (a sleeping session's STATE says
                                     `sleeping`, with its time under the table and as `sleeping` in --json), --check repairs a kill between the
                                     pane map's write and the registry's, --migrate makes the rows of the pane map once (--dry-run first)
  salamander sessions record <id|name> --transcript <claude session id> --why clear|resume|start [--machine X]
                                     a fresh start of a session: the conversation joins the row's list, once (a repeat is a no-op); an unknown
                                     session is an error, nothing written; SALA_SESSIONS=off writes nothing
  salamander sessions transcript <ref> [--json]   read-only: where a session's conversations are on disk, the current one first, then the
                                     earlier ones (the registry's list), with each file's path; the way a side session finds an agent's transcripts
  salamander sessions tag <id|name> [--project <page key>] [--role front|back] [--surface slack|sala] [--project-key <page key>] [--dry-run]
                                     fill project/role/surface of an existing live row (a row spawn --project --role did not make); only the given
                                     fields change; a retired row, an unknown session, a bad role or a bad surface is an error, nothing written
  salamander sessions tag --auto [<id|name>] [--dry-run]   the backfill: every live row with no role (or the one named) gets its project and
                                     role from stackshot's project record (a top-level entry of the agents map is front, one under background: is
                                     back); a role already on a row is never overwritten; a listed row also takes the entry's surface (slack, or none: clears a stale slack); --dry-run prints what it would write; the watch runs it each tick
  salamander sessions resolve <ref> [--live] [--json]   phase 3, read-only: the row a session id (or 8+ char prefix), transcript id, name, alias or
                                     role:<project>/<role> names; exit 0 found, 1 none, 2 ambiguous (candidates listed, nothing picked)
  salamander box SESSION [--json]    read-only: what is in a session's pane input box, as one of three states on the first line: empty · suggestion (dim text,
                                     Claude Code's own suggested prompt that nobody typed; counts as empty; its text follows, labelled) · typed (non-dim text, someone's unsent
                                     words; the text follows). A session reads a pane's box with this command, never with raw capture-pane. Exit 0 read, 2 no live session or pane, 3 no claude in the pane
  salamander where [--json] | --scan | set BOX [--by SESSION] | clear   read: which fleet machine the owner is working from now (one line, "(stale)" after 12 hours,
                                     "no record" when none; --json adds age_s). set records a box (a fleet name): a different box replaces the one where notice every live
                                     session sees once, the same box only refreshes the time; --scan reads the newest ssh-attached tmux client of the last 10 minutes
                                     (the watch tick runs it too); clear removes both (lib/where.sh)
  salamander machines [--json]       read-only: the fleet's machines, one line each: name, board letter, hostname, ssh alias, the host roles it holds (sala-host, stackshot-host),
                                     retired or not, and which machine files name it; a machine one file names and another does not is listed with the missing parts empty.
                                     Reads the owner's files (SALA_FLEET_NAMES and the files beside it, SALA_MACHINE_FOLLOW_MACHINES); needs no running sala and no sala-web. Exit 0, 2 usage or no files named
  salamander host ROLE [--field FIELD | --set HOST]   which machine hosts sala or stackshot now (ROLE: sala | stackshot): the holds script's `host`, so hostname|ipv4|ipv6|ssh, or one value with
                                     --field hostname|ipv4|ipv6|ssh; --set HOST records a new host (only a move does that) through the script's `set-host`, which locks, refuses an unlisted host and
                                     writes nothing then. Its output and exit code pass through unchanged; no running sala or sala-web is needed
  salamander side done [--name NAME] [--item board#N] [--item-updated EPOCH|ISO] [--summary FILE|TEXT|-] [--summary-to NAME|projects/SLUG] [--dry-run]
                                     a side session's write-up gate (lib/side.sh), run by the session itself before it ends: the marker retire asks for
                                     is written only when the board item changed since the start, the project page has a timeline line from the session,
                                     and the summary was sent (by sala, through stackshot's client) to the origin agent or the project's -main
  salamander adopt NAME                           put a live session made by hand (outside spawn) into the pane map
  salamander restore (NAME… | --missing) [--dry-run]  recreate a session from its pane-map row (tmux session in its cwd, a back agent's in SALA_BACK_CWD when that names a directory, then resumed by uuid); --dry-run shows the plan, a session queues it: op restore
  salamander sleep NAME… [--dry-run] | --project KEY [--dry-run] | --list [--json] | --candidates | --pin KEY [--why TEXT] | --unpin KEY | --pins    end the claude of an idle session (nothing in flight; never a front agent by name), keeping its tmux session and pane-map row; a session queues it: op sleep; --project sleeps every session of one project together; --list --json adds, for each sleeper, the lane and model a wake would launch it on; --candidates lists, per project, what the watch's idle sleep tick (SALA_IDLE_SLEEP=on, off by default) would put to sleep; --pin holds a project off it; its stackshot inbox is held, and checked for a waiting line, through stackshot's server on a box that is not the server's (the stackshot client's push_mode decides; SALA_INBOX_MODE files|server overrides), and a server that cannot be asked refuses the sleep
  salamander wake NAME… [--dry-run]               resume a sleeping session by its conversation id (a session queues it: op wake); a name that is not asleep is a message, no action; a project's back agent wakes in SALA_BACK_CWD when that names a directory (see revive); the watch wakes a sleeper itself when a stackshot message line waits for it
  salamander wake --only NAME --cwd DIR [--dry-run]   wake one sleeper in another folder: resumed in DIR and DIR written into its pane-map row, as revive --cwd does; a name that is not relaunched writes nothing (a session queues it, with the owner's words only: op wake)
  salamander follow                               resident watcher of the session registry (sala-follow.service): follows hand renames
  salamander snapshot [--now]        event-driven tmux-resurrect save (tmux hooks + Claude SessionStart hook)
  salamander watch [--check]         the watchdog, from a timer: the operation queue, the automatic update, relaunch and recycle, the
                                     watches below and the post-boot report
  salamander watch --limit | --signin | --net   only the usage-limit watch, only the lane sign-in watch, or only the network-stop wake (lib/watch.sh)
  salamander watch --stuck [--dry-run]   only the stuck-question watch: a pane stopped on a terminal-only question posted once, with its sala-web link
  salamander watch --questions       only the parked-question sweep (lib/watch.sh question_sweep_tick)
  salamander watch --unit-gaps       only the unit-gap pass (lib/watch.sh unit_gaps_tick): same as `job check --post`
  salamander watch --sets [--dry-run]   only the flag rule over the open recycle sets (lib/watch.sh sets_tick): --dry-run prints what it would settle, writes nothing
  salamander watch --back-lanes [--dry-run]   only the back agents' lane rule (lib/watch.sh back_lane_run; OFF unless SALA_BACK_LANE_RULE=on): --dry-run prints what it would queue (a dormant target is replaced by its fallback lane, named with the reason; the front step too, at SALA_BACK_LANE_FRONT_THRESHOLD, default 95), queues and writes nothing
  salamander watch --continued       only the continued-in follow (lib/continuedin.sh cont_tick): a pane that moved to a new transcript id keeps its row
  salamander watch --wrapup [--dry-run]   only the idle wrap-up and clear of background agents (lib/wrapup.sh; OFF by default, runs only with SALA_IDLE_WRAPUP=on): idle SALA_IDLE_WRAPUP_MIN..SALA_IDLE_WRAPUP_MAX_AGE (50..58) min; --dry-run prints what it would type, writes nothing
  salamander watch --sleep [--dry-run]   only the idle sleep tick (lib/wrapup.sh sleep_tick; OFF by default, runs only with SALA_IDLE_SLEEP=on): puts whole inactive PROJECTS to sleep, quiet for SALA_SLEEP_QUIET (172800) s, at most SALA_SLEEP_PER_TICK (1) project per run; --dry-run prints what it would put to sleep, on or off, changes nothing
  salamander watch --wake [--dry-run]    only the wake of sleepers with a stackshot message line waiting (lib/wrapup.sh wake_tick; always on, at most SALA_WAKE_PER_RUN (5) per run); --dry-run prints whom it would wake
  salamander watch --settings        only the settings-apply tick: a changed spec → the settings steps on the boxes behind it (lib/settings-apply.sh)
  salamander settings-apply [--check|--run] [HOST…]   the spec's Claude Code settings steps, applied by sala and never by a session:
                                     no flag = the state; --check prints what it would apply; --run (the unit sala-auto-settings) applies and logs
  salamander heartbeat [--no-push|--dry-run|--check]   sweep every box over ssh: liveness, CLI version, live sessions → the fleet live store (timer)
  salamander ready [--clear|--list]  from inside a session, as the turn's last call: I may be relaunched now (recycle's fast path; shells may be cut, a running subagent never is: it is named and the relaunch waits for it; a pane on the deferred list counts as waiting)
  salamander unpark NAME [--dry-run]  bring a conversation parked by "← for agents" back into its pane (see lib/unpark.sh)
  salamander op <verb> [args…] --from NAME --words "<the owner's words>"   queue a fleet operation for `watch` to run with no model (lib/op.sh):

                                     retire NAME|--id ID [--keep-web] [--busy] [--skip-writeup] [--self] [--leave-items] (a side session: refused until `side done` wrote its marker; --skip-writeup the one bypass; NO --words only for a throwaway: a row with the throwaway tag a bare spawn sets, by any session between turns; a row without the tag, by its spawner, or by any session when NAME is a scratch-*, *-check-*, *-test-* or *-probe-* name (any session: and no live spawner); never with a bypass flag, --keep-web or --id, and only when the project record confirms NAME is on no agents map) · close-shell NAME [--busy] · forget-row NAME · rename OLD NEW · lane <lane> <session>…|<lane> --all|default <lane>|fallback <lane> ·
                                     revive|wake --only NAME --cwd DIR [--force] (--force: revive only): that one session relaunched in DIR and DIR written into its pane-map row; the owner's words only, never --item or --why ·
                                     sleep|wake --only NAME… (--item board#N | --why "<reason>"; no --words) · model <model> [--effort <level>] <session>…|--clear <session>… (several sessions in ONE operation, ONE result notice) or the single-session <session> <model> [--effort <level>]|<session> --clear · provision [--only STEPS] [HOST…] · spawn NAME --project <page key> --role front|back [--mandate FILE|TEXT]
                                     [--lane L] | spawn NAME --side (--fork-of AGENT | --project KEY --item board#N) [--item board#N] [--agents A,B] [--mandate FILE|TEXT] (a side conversation)

  salamander note "<next step>" | --done [<id>] | --clear | --list [--archived]     leave this pane its next step, handed back after

  salamander notice add "<text>" --from NAME [--until WHEN] | list [--full|--json] | drop ID   a one-time line every LIVE session sees at its next tool call or prompt,
                                     with no relaunch (lib/notice.sh; docs/notices-and-hooks.md, "Telling every session something"): one line of at most 400 characters, shown once per

  salamander lane [<lane> <session>…|<lane> --all|default <lane>] [--dry-run] [--rescue]   which account or key each pane's claude runs on

### sala rc --help (exit 0)
sessions can be minted on this box from claude.ai / the mobile app without an SSH hop.

Every pane already registers its own Remote Control session, but a pane can only be created
FROM the box. `claude remote-control` lists the box on claude.ai under Remote Control ("alpha / box-a, N of 32
sessions"; the API calls it an environment) so the app can mint
sessions into. Those are headless children of the server (`claude --print --sdk-url …`), not
panes, and differ in three ways this file absorbs:
  - not covered by tmux-resurrect / `revive`;
  - no reconnection record in their transcript, so a plain `claude --resume` of one forks a
    TWIN on the same transcript (two writers, one file) — elevate with `spawn --fork` instead;
  - the server exits after ~10 min without network; its sessions come back only within ~4 h
    of a stop — hence the restart loop (--run).

  rc --start         clear the marker, then --ensure
  rc --status        server state + served sessions
  rc --restart       SIGINT the server; the loop relaunches on the CURRENT binary (what
                     `revive` does after a CLI update)
  rc --stop          stop loop + tmux session, leave a marker so revive sweeps skip it
  rc --archive ID…   archive claude.ai sessions by web id (session_… / cse_…) via the endpoint
                     (refused for a session a live pane is bridged to); --unarchive ID… undoes it
                     the CLI itself uses (POST /v1/code/sessions/<id>/archive, OAuth bearer from
                     ~/.claude/.credentials.json — never printed). UNOFFICIAL: non-200 → do it on claude.ai.
  rc --titles [--dry-run | --apply (--only NAME (repeatable) | --all)]
                     claude.ai shows each pane's Remote Control session under a title written once, when the
                     bridge session is made, and changed afterwards only by a rename inside the CLI: a pane started
                     with --name never renames, so its title can stay an auto-generated name while its sala name is
                     right everywhere else. Bare: a read-only table of the live bridged panes whose claude.ai title
                     differs from the pane's name (exit 0 either way; a pane whose session is past the first 100

### sala bg-agents --help (exit 0)
usage: sala bg-agents [--dry-run]

       sala bg-agents --reset <project key> [--dry-run]

          <front agent>` a project), takes AT MOST ONE project that is not in back-off or given up, checks the load (1-minute average under
          SALA_BGAGENTS_MAX_LOAD, 10; at or above it the run skips and takes nothing from the ledger), lists the agent <name prefix>-engineer on the project

### sala mq --help --full --help (exit 0)
usage: salamander mq add N… [--flag recycle] [--repo OWNER/NAME]
       salamander mq status [--json] [--repo OWNER/NAME]
       salamander mq drop N [--repo OWNER/NAME]
       salamander mq pause [--reason TEXT] [--repo OWNER/NAME]
       salamander mq resume [--repo OWNER/NAME]
       salamander mq wait N [--timeout SECS] [--repo OWNER/NAME]
       salamander mq doctor [--repo OWNER/NAME]
       salamander mq drive --repo OWNER/NAME        (internal: the driver, started for you)

A queue for the pull requests of a repo that has no GitHub merge queue. It works as GitHub's does: one entry per PR, each stacked on the entry ahead of it (main + PRs 1..k) and
pushed as queue/main/g<seq>, all tested at once (up to inflight_max, six when the rules do not say) by the required check (default `suites`), merged strictly in line order. An entry that
fails is failed alone and the entries behind it are rebuilt on the one ahead of it (`status` shows "(on gN)" for a stacked entry). A PR whose own checks failed (`pr_required`, default
every check on its head) or that conflicts with main is refused when it joins and again before its verdict counts: "refused: a check failed: <name>=fail" / "refused: conflicts with main",
the wait exit 1. A repo's release script uses it the same way: `mq add N`, then `mq wait N`. The rules keys of the removed group mode are retired: `group_max` and `bisect` are ignored with a
warning (delete the line), `queue_mode = "group"` blocks the queue until the line is deleted; `queue_mode = "chain"` is accepted. --repo defaults to the
GitHub origin of the current folder. State: $XDG_STATE_HOME/mergequeue/<owner>__<repo>/ (queue.json, groups/g<seq>.json, events.log).

  Modes (host file $XDG_CONFIG_HOME/mergequeue/<owner>__<repo>.toml, `mode = "off" | "shadow" | "on"`; absent = off). SHADOW builds and tests entries and writes the verdict
  down, with what it WOULD have merged in the journal (`would_merge`); it merges nothing, sets no status and comments on nothing.
  `on` merges (a passed entry goes to main as a fast-forward, never forced; a commit status and one comment on a failure) and is open: `mode = "on"` in the host file makes the driver merge. `off` stays the default and the instant fallback.
  Rules of the repo: .github/mergequeue.toml, read from origin/main (base, required, pr_required, queue_prefix, inflight_max, suites, on_conflict, …).

  add     put PRs in the line, in order (a PR already in it is left where it is); starts the driver, a transient user unit mq-<owner>__<repo>
          (mq-<owner>__<repo>-<run>-<case> with a replay file; systemd-run --user), when none is running. The driver exits when the line is empty and nothing is in flight.
  status  the line, the entries in flight (phase, branch, head, members) and the PRs that finished lately; --json is the same as one object.
          A "REPLAY:" line says a replay file is in use.
  drop    take a PR out of the line (a PR whose entry is in flight stays in that entry's tree until the driver ends the entry, which is never merged with it; the entries behind it are rebuilt without it).
  wait    block until PR N is settled, reading the state file (no GitHub call). Exit 0 = merged, 1 = ejected, failed or dropped (the reason on
          stderr), 2 = gave up (--timeout), not in the line, or the queue is blocked, 3 = tested in shadow mode: its entry passed, nothing was merged,
          4 = replay with ci = "skip": the entry was built, nothing was pushed or tested (never read it as a pass).
  pause   no entry starts and nothing is pushed to main; entries in flight finish testing and wait. resume goes on (and starts the driver).
  doctor  checks the host file, the tools, the state files, the driver and its lock, the repo config as last fetched, queue branches and worktrees
          that no live entry owns (one git ls-remote, of the queue's own queue_prefix only). Exit 0 = all ok, 1 = a problem, each named with the fix.

  Replay (stackshot's `mq replay`, on practice branches of the same repo). The host key `replay = "/abs/path/replay.json"` makes the queue take its RULES (the keys of
  .github/mergequeue.toml, same checks) and the facts of each PR (state, draft, head sha, branch, owner, checks) from that file instead of origin/main and GitHub, so a PR that
  is already merged can join; no GraphQL call. Each head is fetched by its sha. SHADOW ONLY: `mode = "on"` is refused, nothing is merged, set as a status or commented, and no push
  goes outside queue/practice/. rules.base must start with practice/ and rules.queue_prefix with queue/practice/, else the queue is blocked. The file: {"version": 1, "run": R, "case": C,
  "ci": "real" | "skip", "rules": {...}, "prs": {"<N>": {"state", "draft", "head", "branch", "owner", "checks": {name: pass|fail|pending|cancel}}}}; an unknown key or a bad value is refused
  with the message. ci "skip" ends an entry after it is built (no push, no CI): the PRs are "tested (CI not run)", `mq wait` exit 4. docs/mq.md has the schema.

Every GitHub call an entry makes is counted in its record (gh_calls, salamander_calls) and journaled; in the normal case an entry costs one GraphQL
read for the build, one for the recheck before its verdict counts, and the check-runs reads of its head, none while the CI-run poller's file shows the run going. Git over the remote is not a GitHub API call.
