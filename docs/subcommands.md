# Subcommands

Every sala command with its options, one row each.

| `spawn [NAME] [--mandate F\|T [--no-confirm]] [--cwd D] [--lane L] [--model M] [--effort E] [--fork UUID] [--dry-run]` | new tmux session running `claude`, named with `/rename`, verified in the registry. **The mandate** (Thu Oct 15th 2026): a readable file is read by the session itself — the orientation line `Read <absolute path> in full — that is your mandate for this session …` is typed and the session waits for a confirmation unless `--no-confirm`; anything else is text typed as the first message. `--brief F` (a file only) and `--prompt T` (text only) are its older names, kept as aliases. The orientation line and a text are typed with `<!-- sala -->` in front, as every message sala types is (see Design notes). `--lane L` launches on that lane and records the row (`sala lane` would otherwise); `--model fable` is refused on any lane but Ultra (`subscription-1`: Fable runs only there); `--dry-run` runs every check and prints the plan, makes nothing; `--fork` elevates an existing conversation into its own transcript. **A throwaway's spawner** (Thu Oct 29th 2026): a bare spawn (no `--project`, `--role` or `--side`) run by a Claude session writes that session's tmux name onto the new registry row as `spawned_by` (unpublished, like the `side*` fields; `docs/session-registry.md`); that is what lets the same session end the throwaway with `sala op retire NAME --from YOU` and no words. A spawn from a plain shell or a human's pane records none. **The throwaway tag** (Fri Oct 30th 2026): the same bare spawn, from any caller, also writes `throwaway` = `1` onto the row (unpublished); a spawn with a project, role or side flag never does, and a later `sessions set`/`sessions tag` that gives the row a project, role or side mark clears it. Any live session may then retire a tagged row with no words (see `retire`) **Spawn gate**: a name that is not a throwaway's (`scratch-*`, `*-check-*`, `*-test-*`, `*-probe-*`, none given), not a side session and not sala's shell must be on stackshot's project record before its pane exists; `--role <word> [--front\|--back] --mandate F\|T` registers it (`post project-agent`, label `sala-spawn`, started only on the 200, read back; any other answer exits 6 with stackshot's reason and no pane), without them it is refused (exit 3) with the reason and the register command. `--suggest-name` asks stackshot's name check when it is live and falls back to sala's own suggestion. |
| `spawn NAME --project <page key> --role front\|back [--surface sala\|slack] [--mandate F\|T] [--lane L] …` | **a project agent's session** (`lib/spawn.sh`, the one path `sala op spawn` and the web form take). A project agent is registered with stackshot (`client.py post project-agent`, which lists it on the project's agents map as a front agent, the ones the owner talks to, or a background one). Before the tmux session is made, never fail-open: the name (lowercase letters, digits and dashes, at most `SALA_AGENT_NAME_MAX` = 48 characters; a suggestion, not a check: `--suggest-name` prints `<prefix>-main` only for a front agent of a project that has no agent yet (a fresh stackshot record lists it with none, or `--new` says the project has no page yet), else `<prefix>-<random word>` (a word picked at random from sala's list, not in a fixed order), and never a name that is taken (a tmux session, a running claude, an agent on any project's map in stackshot's record); a missing, stale or silent record is no ground for `-main`, so it answers a word; when stackshot's name check answers and calls none of the candidates valid (taken, a prefix it does not know, a retired, hidden or hub project) no unchecked name is returned: its reasons are printed and the exit is nonzero (a check that cannot answer keeps sala's own suggestion); a real spawn with no NAME keeps the older rule, a front is `<prefix>-main`; the prefix is the project's real one from that record, its `-main` agent's name without `-main` (`demo-docs` for projects/demo-docs), else the page-name convention (`<scope>-<slug>`); `--prefix P` sets it for a caller that knows it (the web form does)), the name is on THAT project's map — read from stackshot's project record alone (no page is asked and no `pages.py` is run; since this change sala no longer answers `NO-PAGE: <key>` or exit 4: a project the record does not have is a record that cannot answer it, below) (asked of stackshot first; only when stackshot cannot be reached the file copy `~/.local/state/stackshot/projects.json`, `SALA_PROJECT_RECORD`, no older than `SALA_PROJECT_RECORD_MAX_AGE` = 600 s, its age said: name listed, `front` agreeing with `--role` or the spawn is refused with exit 1; an agent registered through stackshot's `post project-agent` whose page line is still owed counts as listed); a record that cannot answer (missing, stale, unreadable, no such project) **fails closed** for a name the closed exception list below does not cover: exit 6 and no pane, "stackshot's project record cannot answer (<why>): … retry when it is fresh, or `SALA_AGENT_CHECK=off` to start it unchecked" (a spawn that carries `--role` and `--mandate` still registers through stackshot as below, which needs no fresh record; only its read-back does, and when only the read-back cannot be made the message says the name IS registered and to run the same spawn again); not listed → with a mandate (`--mandate`) and a stackshot client sala registers it itself (THE SPAWN GATE: `client.py post project-agent <key> <name> --role <word> --front|--back --mandate "<line>" --sender sala-spawn`, back by default; the pane starts only on stackshot's 200 and the record is read back first; a refusal, an unreached stackshot or a failed read-back is exit 6 with no pane; a repeat of the same spawn is safe, stackshot answers 200 again for the same side and mandate, and when the pane cannot be made after the registration the message says the name is registered and to run the same spawn again), else (no mandate, or no client) exit 3, the refusal on stderr naming one command and, on stdout, `REGISTER: <key>` followed by that command, stackshot's `python3 ~/stackshot/stackshot/fleet/client.py post project-agent <key> <name> --role <the part of the name after the project's name> --front|--back --mandate "<the mandate's first line, cut to 70 characters>"` (the role is `<role>` when the record gives no project name to cut by, the mandate `"<one line>"` when the spawn had none); in that refusal sala does not run it and never asks for a page edit; nobody is messaged: the older message to the project's keeper, `SALA_SPAWN_ASK_CMD` and `SALA_SPAWN_ASK_EVERY` are gone); a back agent needs a mandate and starts on it (nobody confirms a background agent), in the directory `SALA_BACK_CWD` names when `--cwd` is not given (unset by default, so `$HOME`; set it to the directory whose `CLAUDE.md` is the background brief, so the agent loads that brief and not the front rules of `$HOME`). A `SALA_BACK_CWD` this machine does not have refuses the spawn (unset is the only way to start in `$HOME`; `--cwd` always wins), and the pane map's cwd column records the directory it started in, so `sala restore` recreates the session there; a name already live is refused as for any spawn. **The surface** (`--surface sala|slack`): where a front agent talks with the owner. `sala` is the default and is not stored; `slack` marks a front agent that answers the owner's Slack app messages. It is valid only with `--role front` (a back agent is refused: a Slack agent is a front agent), not with `--side`, and any other value is refused. The surface is the flag's or, with no flag, the one the project record gives the name (the entry `sessions tag --auto` copies onto the row later), so a registered Slack agent spawned without `--surface` is a Slack agent too; a `--surface` that conflicts with the record's is refused, naming both values, and so is an entry whose surface sala cannot use (a value it does not know, or one that is present but empty, `""` or null: only an absent field means `sala`; the reason and the project record named; a record that is missing, stale or does not list the name refuses nothing). The lookup reads only the project record, never the session registry, so a registry that is missing or unreadable cannot move the start directory. A Slack agent starts in the directory `SALA_SLACK_CWD` names when `--cwd` is not given (the directory whose `CLAUDE.md` is the Slack brief, so the agent loads that brief and not the rules of `$HOME`); the key unset, or naming a directory this machine does not have, refuses the spawn with a message naming the key, and there is no fallback to another directory (`--cwd` always wins). The pane map's cwd column records the directory, so a revive or `sala restore` starts it there again; the registry row carries `surface: slack`, `spawn --list` and `sessions` mark it `[slack]`, and the register command the refusal prints carries `--surface slack` (`sala op spawn` takes the flag too). Once the session is up and mapped, `SALA_SPAWN_REGISTER` (unset by default: a no-op that logs `spawn-register: no hook configured`; the registration is the spawn gate's own `post project-agent`) runs with the name, page key, role and mandate file as arguments and `SALA_SPAWN_*` in its environment; a hook that fails is one ⚠ line, never the exit status. A plain spawn (no `--project`) is decided from the record first the same way (listed: it starts; not listed with `--role` and `--mandate`: registered, then started; else exit 3 with the register command). The closed exceptions (`agent_gate_exempt`: `scratch-*`, `*-check-*`, `*-test-*`, `*-probe-*`, an auto-generated name, `--side`, sala's shell session) skip the requirement to be registered, but a `--project` spawn of an exempt name the record lists is still held to the record's role. A plain spawn whose record cannot answer fails closed the same way (exit 6, no pane) when stackshot is on the box; a box with no stackshot at all (no record file and no client: `docs/running-without-stackshot.md`) has nothing to ask and is not checked. |
| `spawn NAME --side (--fork-of AGENT \| --project <page key> --item ID) [--agents A,B] [--mandate F\|T] …` · `spawn --suggest-name --side …` | **a side conversation** (called a Quick session on the web page; [docs/side-sessions.md](side-sessions.md)): a short-lived session started in one step to talk something over, on no page's agents map and with no role. Two starts: a **fork** of a running agent's conversation (`--fork-of`, named `<agent>-side-<word><nn>`, its summary to the agent), or a **fresh** session about a board item scoped to its project page (`--project` + `--item`, `--agents` the item's involved agents, named from the project's main agent, its summary to that agent). Its mandate file says to read the page's Current state and the item, to read only the transcript excerpts it needs from the involved agents (`sessions transcript`), to run `side done` before it ends, and to retire only on the owner's word. No quiet watch, no auto-retire, no cap. Through the queue: `sala op spawn NAME --side …` (checked at queue time, planned with `--dry-run`). |
| `side done [--name NAME] [--item ID] [--item-updated EPOCH\|ISO] [--summary F\|T\|-] [--summary-to NAME\|projects/SLUG] [--dry-run]` | **the write-up gate of a side session**, run by the session itself: writes `$SALA_STATE_DIR/side/<name>.done` only when the board item changed since it started, the project page has a timeline line from it, and the summary was given (sala sends the receiver a one-line pointer itself, once, as stackshot's `--fyi` with no `[for <owner>]` mark, so it starts no turn; a `projects/<slug>` target gets the full body; an `--fyi` stackshot refuses is said with a ⚠ line and the marker is written anyway). Every failed check is said. `retire` of a side session is refused until the marker is there (the queue's plan too); `--skip-writeup` is the only bypass. [docs/side-sessions.md](side-sessions.md) |
| `spawn --list` | live sessions (name, version, claude.ai URL) + tmux sessions whose claude has exited, with the resume hint. A **sleeping** session's pane (its claude ended on purpose; see *Sleeping sessions* below) is listed as `NAME (sleeping) sleeping — its claude ended on purpose; not revived`, never as an exited claude to revive |
| `revive [--dry-run] [--force] [--only NAME] [--lane-default] [--rescue]` · `revive --only NAME --cwd DIR [--force] [--dry-run]` | resume dead panes; `/exit` + resume stale-binary panes when idle; restart the RC server on a version change. Every pane's plan says `lane: <the lane its claude runs on now> → <the lane the resume line puts it on>`; a pane with no lane row whose claude runs on another lane than the default is refused (that pane only, in the skipped rows and the recycle's post) with the fix — `salamander lane <lane> <session>` records it, `--lane-default` accepts the default; a row wins as the recorded intent (see *Lanes*). `--dry-run` prints the verdicts and relaunches, schedules and writes nothing. `--rescue` (with `--only`, never a recycle): a stale background-task row no longer holds the pane — the CLI's exit dialog, the Stop hook's record and the mod all list a shell stopped by hand or a subagent long gone; when no child process runs under the pane's claude, the dialog is confirmed ("Exit and stop tasks") and the record and the mod's refusal are read as stale, each said in the output; a live child keeps every refusal (see *The rescue* under *Lanes*). **A claude that ignores `/exit`:** when the pane's claude is still running `SALA_EXIT_WAIT` seconds (30) after the `/exit`, the sweep ends that one process by its pid (SIGTERM, SIGKILL after `SALA_EXIT_TERM_WAIT` seconds, 10, if it is still there) and resumes the conversation by its id as for any pane, with one line in the output and one post (the session, the pid, the lane it resumes on); `--dry-run` says "will end a stuck process". The pid is the one resolved from the pane (its claude, `/proc/<pid>/exe` a Claude Code install, the pane's environment) and checked again right before the signal, never a process found by name; never the session that runs the command or an sdk-lane CLI; a pane whose registry row says a turn or background work is running is not a hang and is skipped as before (the idle gates come first). `SALA_EXIT_END=0` turns the step off (the pane is skipped with the reason, as before) **The sweep's order** (`ordered_panes`): least recently active first, by claude.ai's `last_event_at` for the pane's bridge id and else by the transcript's mtime. The bridge id is read from the END of the transcript in pieces of 4 MiB, at most `SALA_BRIDGE_SCAN_MAX` (64 MiB) back; the whole transcript was once read into memory for every pane on every revive, and a conversation of several hundred MB took gigabytes. A transcript whose last bridge record is further back falls back to its mtime, like a pane with no bridge.. **A session moved to another folder** (`--cwd DIR`): sala puts that one session's relaunch in DIR (the line it types is `cd DIR && <resume line>`, so no `cd` is typed by hand; a tmux session that is gone is created in DIR, from the row's conversation) and, once the claude is up, writes DIR into the pane-map row of the resumed conversation, so a later `restore` starts there (under a freeze the write is deferred like a follow). Nothing else changes a row's folder at a relaunch: sala reads no folder from a pane or a process, and a relaunch without `--cwd` writes none. Allowed only with exactly one `--only NAME`; DIR is an absolute path to an existing directory that can be read and entered, with no control character in its name; refused too with `--self` and the worker flags, for a name with no pane-map row, for a sleeper (`wake --cwd` is its verb) and for the Remote Control session. The plan shows `pane-map folder OLD → DIR`. A live claude on the current version needs `--force`, as without the flag. A `--cwd` run is never retried or deferred: a target that is not relaunched (busy, refused, the resume failed) writes nothing, says so and exits 1, and so does a dry run that would relaunch nothing; run it again. Through the queue it needs the owner's words (`op` below) |
| `revive --save-map` | observe the pane map against the live registry (wire to resurrect's post-save hook): a mapped session whose live claude runs a different conversation than its row has the row follow; nothing is added or dropped — the map is a ledger (see *Design notes*) |
| `recycle [--update] [--force] [--lane-default] [--dry-run]` | `--update` runs `claude update` first (a live process keeps the binary it launched with, so updating and relaunching are one operation); then one detached driver: sweeps every other pane now, relaunches the pane you ran it from once it goes idle; `--force` relaunches every idle pane, not only stale-binary ones (a relaunch is also how a pane re-reads `CLAUDE.md`, skills and settings). `--dry-run` is a dry-run driver: the sweep's verdicts and the self-worker's plan for your pane in the log, and nothing else — no `claude update`, no freeze of the pane map, no relaunch, no set, no post. A back agent's pane that a turn or its background work keeps busy is waited for `SALA_PAUSE_AFTER` s (default 900, 15 min; `0`/`off` keeps the old wait), then the relaunch interrupts the turn with one Escape, relaunches the session and leaves it a note written by the relaunch (what it was doing, and the inbound messages held for it meanwhile); `SALA_PAUSE_SCOPE` (`background` default: back agents only, a front agent is never paused; `all`; `off`) says whose turn may be paused, and `SALA_NO_PAUSE` names sessions never paused (*The pause* in `docs/recycle.md`). Panes skipped for a transient reason (a turn running, idle < 10 s, a background child or agent, a running subagent, an unsubmitted draft) are retried by a detached worker every `SALA_RETRY_EVERY` s for `SALA_RETRY_WINDOW` s with the same gates. A pane that said `sala ready` but is held only by background shells (registry state `shell`) goes on the deferred list at once, and a pane still pending when the window ends is deferred too, not given up: both stay outstanding in the recycle's set, the report names each as deferred with its reason, and `watch` relaunches them once they are free (only the 8-day drop of the deferred list gives one up). A pane on that list is tried when `watch` finds it free: it first asks the in-session mod, and a turn the mod names (a subagent no process list shows) holds the pane, said once in the log with its holder; an exit the mod keeps refusing for a turn it cannot name goes by keys after `SALA_STALE_TURN_AFTER` (3) refusals while every other check reads the pane as idle, and the tries thin out to one in 10 min, then one in 30 min (*recycle*, "One idea of busy"). A pane that stays on that list is not left silent: `watch` tells it again an hour after it was set aside (`SALA_LATER_RETELL`; the recycle's line, through the waiting flag and pushed into the idle session), at most `SALA_LATER_RETELL_MAX` (3) times, and once it has been held `SALA_LATER_LIMIT` s (default 3 h) posts once to the usual notify path with the pane, claude's and sala's versions, how long, and the commands holding it; a pane that relaunches leaves the list and clears all of it. A routine flag (the watchdog's auto-recycle or automatic CLI update) with N of at least 3 panes in scope closes when exactly one is left, `N-1 of N relaunched`, naming that pane as still holding; it goes onto this list and `watch` relaunches it once it is free (*Recycle flags and the recycle job* in `docs/recycle.md`; a recycle or update from the owner's words closes only when every pane is done). A pane given up for good (its pane gone) or one that needs a human (a terminal prompt, an unmappable pane) is reported, not retried. The sweep runs in three phases: every pane's gates checked in parallel, the eligible panes closed (`/exit`) in parallel (first the stackshot inbox of every eligible pane is held, the sweep waits `SALA_HOLD_SETTLE` s, default 3, for a line stackshot handed out just before the hold to become a turn, and each pane is checked once more just before its `/exit`: a pane that is busy by then is left alone and retried, never exited over its turn), then the resumes typed one by one, least-recently-active first, `SALA_RESUME_GAP` s apart (default 1; at most `SALA_SWEEP_JOBS` parallel jobs, default 12) — the log carries a timing line per phase. A claude still running after the `/exit` wait is ended by its pid and the session resumed, as `revive` does (`SALA_EXIT_END=0`: skipped, as before). |

Refused like any pane when its lane line is a mismatch with no row. `--dry-run` prints what the self-worker would do and starts none; the worker waits up to `SALA_SELF_WAIT` s (default 900) for the pane to go idle, holds its stackshot inbox, waits `SALA_HOLD_SETTLE` s and looks again (a pane busy then is released and handed to the retry worker), and the waits stack to at most three times `SALA_SELF_WAIT`; `--rescue` reaches the self-worker (a stale task row of your own pane) |

| `rc --titles [--dry-run \| --apply (--only NAME (repeatable) \| --all)]` | the claude.ai title of each live bridged pane against its sala name. claude.ai writes a Remote Control session's title once, when the bridge session is made, and afterwards only a rename inside the CLI changes it; a pane started with `--name` never renames, so it can keep an auto-generated title (`swift-jaunty-charm`) while its sala name is right everywhere else. Bare, it is a read-only table (NAME, claude.ai title, status) of the panes that differ, exit 0 either way (`all N bridged panes carry their sala name` when none; a pane whose claude.ai session is not in the first 100 the API lists is counted as `not listed`, never guessed). `--apply --only NAME` (repeatable: `--only a --only b`) sets just those titles to the pane's name (`PUT /v1/code/sessions/<id>` with `{"title": NAME}`, the same unofficial endpoint family as `--archive`; OAuth bearer from `~/.claude/.credentials.json`, never printed), then re-reads and prints `ok` or `FAILED` per pane; a non-200 prints its status and the first 200 characters of the answer. `--apply` with no `--only` is refused, a bulk apply needs `--all`. `--dry-run` is the bare form spelled out; with `--apply` it is refused (no request is sent). A name that two live panes carry is refused before any PUT, with the clash listed. With `--all`, a pane whose claude.ai session is not in the first 100 is reported `FAILED ... not listed` and the exit is 1, never a silent pass. Only a name in `[a-z0-9-]` with nameSource `user` is set; a title already equal is left alone (idempotent). `sala spawn` runs `--apply --only NAME` once the new pane's bridge id is known, best effort: a failure is one warning line and never fails the spawn. `SALA_ANTHROPIC_API` (default `https://api.anthropic.com`) moves the API for a test |

Remote sessions keep their old binary until restarted by hand; package managers are never touched |
| `provision [--check] [HOST…]` | headless `/provision` on each other machine over ssh (`claude --dangerously-skip-permissions -p "/provision"`), one at a time; offline hosts skipped; per-host log. It lives in sala so that one permission rule for `sala` pre-approves it for every host — see *Permissions*. | `retire NAME\|--id ID [--keep-web] [--busy] [--skip-writeup] [--self] [--leave-items] [--dry-run]` | end a Claude session for good (a tmux session with no Claude in it is `close-shell`, a leftover pane-map row is `forget-row`): `/exit`, kill the tmux session, drop its pane-map row (the only path that does), snapshot, archive its claude.ai session. Without this a session that exits **comes back** at the next revive — that is revive's job. The transcript survives (`claude --resume <uuid>`). `NAME` is the **exact** tmux session name, never a registry name or a prefix of one: a name that is no tmux session is refused (with a pane-map row it names `sala forget-row NAME`, without one it says to use `--id`), and a tmux session with no claude in it is refused naming `sala close-shell NAME`. `--id ID` (a full conversation uuid or an 8+-character prefix of it; not together with NAME) is the other way in: the CLI's session registry (`~/.claude/sessions/`) resolves it to the tmux session and pane, and the choice is said before anything is done (id → registry row → tmux session, pane). Two live rows answering to the id, a prefix on several, or a resolved tmux session that holds another live claude stop it with the candidates listed and nothing touched (retire guesses none); a row whose process is gone, that records no tmux pane, or whose pane is another server's is said and not acted on. **Guardrails**, each with its own flag (the old `--force` did two unrelated things and is refused with a sentence naming both): `--busy` retires a pane that is not idle; `--skip-writeup` retires a side session before `sala side done`; `--self` lets a session retire the one the call runs in (found by process ancestry, never `TMUX_PANE` alone; no /exit is typed into its own pane, the output goes to `~/.claude/salamander-retire.log` and the call ignores HUP and PIPE while its pane closes), refused without it, and when the session is mid-turn (the call is part of that turn) its own running turn is not counted as busy: a dialog, a background shell or a child process still is and needs `--busy`. The items check runs under `--dry-run` too. `--dry-run` types, kills, writes, snapshots and archives nothing and names each action it would take (the pane, the pane-map, lane and model rows, the snapshot, the claude.ai session) or the refusal it would give. ## Sleeping sessions

A session may **sleep**: `sala sleep` ends its claude on purpose, its tmux session and its pane-map row stay, and `sala wake` resumes its conversation by its id. Both are fleet operations a Claude session queues with `sala op sleep|wake --only NAME (--item board#N | --why "<one line>") --from YOU`, with a reason on the record and no words from the owner; a whole project's sleep, `sala op sleep --project KEY --from YOU --words "<the owner's words>"`, takes his words and no reason door (*The asked sleep*, below) (the same door as `revive` and `restore`: the session asking is placed by process ancestry; never the asker; `sala op wake` of a session that is not asleep queues nothing). Nothing puts a session to sleep on its own unless `SALA_IDLE_SLEEP` is turned on, and then the watch sleeps whole inactive projects, never one session (below). Stage 3 made a sleeper visible everywhere sessions are listed (*Display*, below).

- **The marker** is the file `$SALA_SLEEP_DIR/<conversation uuid>` (default `$SALA_STATE_DIR/sleeping/`), one line: `<ISO-Z time> <name>`. The pane map keeps its four columns and the session registry file (`$SALA_STATE_DIR/sessions.json`) is untouched; what the heartbeat publishes carries the fact, one optional `sleeping` key (*Display*, below). The helpers are in `lib/common.sh`: `is_sleeping SESS` (a tmux session name or a session name), `sleeping_mark UUID NAME`, `sleeping_clear UUID`, `sleeping_list`, `sleeping_rename UUID NAME`.
- **Nothing in sala revives, restores, fails or counts a sleeping session as missing.** `no_relaunch` is true for it, so the bare-pane heal, the revive sweep, `stale_panes` and the other checks of a pane without a claude leave it alone; where "left alone" would be wrong it is handled by name: a recycle set, the retry worker and the deferred list settle it as `gone` (it no longer counts, never `gave`); `restore` and the compare after a reboot name it as sleeping and recreate nothing (`restore --missing` does not list it); `revive --only NAME` refuses it as it refuses a `SALA_NO_RELAUNCH` session; `lane` and `model` write its row only and relaunch nothing (`sleeping: recorded only`); `retire`, `close-shell` and `forget-row` end it with no `/exit` and clear its marker; `rename` works with no claude (nothing is typed; the marker's name follows); `adopt` and `box` say it is sleeping where they said there was no claude; `sala op revive|restore` says `wakes in a later stage` and queues nothing (see `op`).
- **Display** (stage 3; the contract is interface 35 of [stackshot-contracts.md](stackshot-contracts.md), version 52). A sleeping session is never shown as idle, dead or crashed, and each place that lists sessions says so:
  - `sala sessions` shows `sleeping` in the STATE column and, under the table, `sleeping: NAME since Sun Nov 22nd 15:10 KST (…; sala wake NAME resumes it)` (the time in `SALA_TZ`, this machine's zone when unset); `sala sessions --json` adds `"sleeping": "<ISO-Z>"` to the row of a sleeper and to no other (its `state` stays `live`); `sala spawn --list` shows `(sleeping)` and the lane and model lists say so.
  - The heartbeat publishes it: `sessions.json` (interface 1) gets a row for a sleeper keyed by its conversation uuid (it has no live registry file, so it had none before), with the usual `name`, `url`, `seen`, `machine` and `"sleeping": "<ISO-Z>"`; `session-registry.json` (interface 19) keeps `state: live` and adds the same key. A marker whose uuid is on no pane-map row of the box is stale and makes no row; a conversation a live row already has is listed once.
  - The web page (sala-web; `web/README.md`, *Sleeping sessions*) lists a sleeper in the sidebar and the Overview marked `sleeping` with the time in the page's zone, and **opening it shows its conversation (read from its file on disk) and wakes nothing; a message sent to it, or its Wake button, wakes it**: the page asks `POST /api/wake`, which queues `sala op wake --only NAME --from sala-web --words "<owner>, via the sala web page: …"` as the owner's own act, then follows the operation until the session is live and opens it; a message sent while it slept is held in the page and goes in once the session is back.
  - Stackshot may read exactly: the marker directory and line, the `sleeping` key of `sessions.json` and of `sala sessions --json`, and the wake `sala op wake --only NAME (--item board#N | --why "…") --from YOU`. `sala reboot --status` lists the reboot hooks and the last run's step, not sessions, so it shows nothing of a sleeper.
- **The watch's sleep passes** (stage 5; `lib/wrapup.sh`, run by `lib/watch.sh` after the wrap-up step, both through the verbs' own code: the watch runs `sala sleep NAME` and `sala wake NAME` as the CLI, so the same refusals and re-checks apply, and neither needs a queue marker or the owner's words, being the system's own routine):
  - **The asked sleep** (`sala op sleep --project KEY --from YOU --words "<the owner's words>"`; the unit runs `sala sleep --project KEY --asked`): when the owner says to put a project to sleep now, a session queues it with his words and the project sleeps without waiting out the quiet rule. KEY is the page key with or without `projects/`. It is the whole project, front agents and background agents together, never one session of it, and it is solo: it holds the recycle lock, as the sessions are known only when it runs. His words lift two things and nothing else: the quiet rule (`SALA_SLEEP_QUIET`) and the settle time (`SALA_SLEEP_AFTER`; a session only has to have ended its turn, `SLEEP_ASKED_SETTLE`, 3 s ago). Still refused, with nothing touched: a pinned project (his words do not lift a pin: `--unpin` first), a project with no reading of its activity, and any session with work in flight (background work, dialog, typed text, scheduled job, queued operation, stackshot message line, limit or network stop, open question) or a kind that never sleeps (Remote Control, side, sdk lane, `SALA_NO_RELAUNCH`). The asking session may be one of the sleepers: the plan (`sala op --plan sleep --project KEY`) says "the asking session sleeps once idle", the runner (outside every pane) waits up to `SALA_SLEEP_ASKER_WAIT` (90 s) for its turn to end, then sleeps the whole project with the asker last; an asker still busy then leaves the whole project untouched, and no result line is sent into a sleeping asker's inbox (it would wake it: the Slack post and the op log stand). `sleep --only YOU` with the words works the same for a background agent asking about itself; a front agent alone is still refused. A plain `sala sleep --project KEY` (the tick's rule) is unchanged and refuses a project that is not quiet.
  - **`sleep_tick` is off by default** and sleeps **projects**, not sessions: nothing sleeps on its own unless `SALA_IDLE_SLEEP=on|1|yes|true` is set in the config (`config.example`; `sala config` prints it). When on, each watch run puts to sleep **every session of a project, front agents included, together**, and only when all of these hold: (1) the project is **quiet**: its last external anchor notice and its owner's last input are both older than `SALA_SLEEP_QUIET` (172800 s, two days); audits, router notices and messages between agents are not activity; (2) **every one of its live sessions** is accepted by `sleep_ready` in project mode (idle for `SALA_SLEEP_AFTER`, 3600 s, with nothing in flight: no background work, dialog, typed text, scheduled job, queued operation or note, pending relaunch, stackshot message line, limit or network stop, open question; not a Remote Control, side, sdk-lane or `SALA_NO_RELAUNCH` session), and not woken less than `SALA_SLEEP_AFTER` ago (`sala wake` writes a wake stamp, `$SALA_SLEEP_DIR.woke/<conversation uuid>`, the epoch second, next to the marker folder), so work in flight in any one session keeps the whole project awake; (3) the project is **not pinned**. A background agent is never selected alone, and a session with no project never sleeps by the tick. Sessions are grouped by the project of their registry row (else the project record's, else the roles file's; `sessions.py project-sessions`). **At most `SALA_SLEEP_PER_TICK` (1) project per run**, the quietest first, so the first run on a fleet does not stop it all at once. The tick stands aside while a revive, retire, rename, spawn, lane, model or reboot or a queued operation runs, the pane map is frozen or a restore runs (`bare_busy`). A project whose sleep was refused or failed is asked again after `SALA_SLEEP_RETRY` (1800 s); the next project takes its place meanwhile. One watch-log line per project (`sleep: put project KEY to sleep (N session(s); quiet for H h)` or `sleep: project KEY not put to sleep — <reason>`); no post.
  - **The activity source** is one function (`sleep_activity_load`, `lib/wrapup.sh`): the command in `SALA_ACTIVITY_CMD`, else stackshot's `client.py project-activity --json` (found through `SALA_STACKSHOT_CLIENT` / `SALA_STACKSHOT_DIR`), run through `sh` with a `SALA_ACTIVITY_TIMEOUT` (30 s) limit. The JSON is `{"projects": {"<key>": {"anchor": <epoch or null>, "owner": <epoch or null>}}}`; a project the answer does not list has had neither (never) and counts as quiet. **It fails safe**: a command that fails (its stderr line is shown), prints nothing, prints something that is not that shape, lists no project at all (an empty answer is not trusted) or does not answer in time makes the tick sleep nothing, and `sleep --candidates` and `watch --sleep --dry-run` say why. Two things the call cannot see: a CI result on an agent's own pull request counts as an external anchor notice, so it keeps its project awake; and a front agent whose chat stamps do not sync (a Slack-surface one) is invisible to the call, so pin such a project if it should not sleep.
  - **Pins** (`sala sleep --pin KEY [--why TEXT]`, `--unpin KEY`, `--pins`): a pinned project never sleeps by the tick and is shown as pinned; `sala sleep --project KEY` refuses it too.
  - **`wake_tick` is always on**, because a sleeper can also come from a manual `sala sleep`: a sleeping session with a stackshot message line waiting for it (`inbox_line_waiting`, the predicate `sleep_ready` uses for "no message waiting": a line in `hub/` or `msg/` of `SALA_STACKSHOT_INBOX` whose `to`, `uuid` or `name` field equals the session's name or its conversation id, held or not; a line for `worker-extra`, or one whose text only mentions `worker`, is not one for `worker`) is woken with `sala wake`, **at most `SALA_WAKE_PER_RUN` (5) per run**, once per run each, a failed one not before `SALA_WAKE_RETRY` (600 s). The candidate is picked by conversation id, so the pane-map row of the name is checked to still hold that id just before the wake (a row replaced meanwhile is skipped, with no failure stamp). `watch --sleep --dry-run`, `sleep --candidates` and `watch --wake --dry-run` skip a session that is in its retry wait, as the real run does, and say so. The inbox files are never touched: the line stays queued until the resumed pane takes it. A notice (`sala notice`) does not wake a session; a session that is not asleep is untouched. **Waking is per session**: a message line for one sleeper of a project wakes that session only and the rest of its project stays asleep; the woken session holds its project back for `SALA_SLEEP_AFTER`, and once that is over the tick puts it back to sleep with the project. One log line per wake (`wake: woke NAME — inbox line waiting …`). With nobody asleep it costs one directory check. Stackshot only writes the message, as it does today, and never runs a sala verb to wake one.
  - **See what the tick would do before turning it on:** `sala sleep --candidates` or `sala watch --sleep --dry-run` (the same list, one line per project, the quietest first; the first `SALA_SLEEP_PER_TICK` would sleep on the next run, the rest wait), and `sala watch --wake --dry-run` for the wakes. Nothing sleeps unless `SALA_IDLE_SLEEP` is turned on in a config; a sleeper stays asleep across a reboot (stage 1: no revive, restore or heal brings it back).
- **`sleep_ready SESS`** (`lib/wrapup.sh`; asked by `sala sleep`, twice: before the stackshot inbox is held and again once it is) prints the first reason a session may not sleep now and returns 1, or returns 0 with no output: no session, already asleep, the Remote Control session, managed outside sala, a side session, a front agent (named alone; in project mode the tick drops this refusal, a front agent sleeping with its quiet project), not in the pane map, no claude, a Remote Control served session, the sdk lane, no conversation id or idle time in its registry row, idle under `SALA_SLEEP_AFTER` (3600 s), a busy turn or text typed in its box (`wrap_ready`'s own checks), a scheduled job left by its last turn, a queued operation that names it, a note waiting, the deferred list, an open relaunch set, a relaunch flag, a stackshot message waiting (`SALA_STACKSHOT_INBOX`), a usage-limit or network stop, a question open on its screen.
- **On a box that is not stackshot's server** the hold in `sala sleep` and the "a message waits" check of `sleep_ready` and the wake pass go through the server's client calls, and a server that cannot be asked refuses the sleep and does not wake or count a failed wake: see *Inbox holds across machines* below (the stackshot client's `push_mode`; `SALA_INBOX_MODE` overrides it).

## Inbox holds across machines

`recycle`, `revive`, `sleep` and `wake` hold a session's stackshot inbox while its claude is down, and `sleep_ready` / the watch's wake pass ask whether a message line waits for it. On the box that runs stackshot's server both are files (the held files of `SALA_INBOX_HOLD_DIR`, the message folders of `SALA_STACKSHOT_INBOX`). On any other box neither folder is the server's, so sala asks the server through stackshot's client API instead (`lib/inboxhold.py`, called by `lib/common.sh` and `lib/wrapup.sh`). Nothing changes on the server's own box. The server's side of the calls is stackshot's `docs/inbox-holds.md`.

- **Where: the stackshot client's own setting, no second one.** A box that sends its lines to the server (`[client] push_mode = "server"`, or `"auto"` with a client URL that names another machine) holds there too; `push_mode = "local"`, stackshot's default, is the one-box way and holds in files. sala reads what the client reads: `$ANCHOR_PUSH_MODE`, else `[client] push_mode` of the stackshot config (asked of the client's own code when this box has the stackshot checkout, else of `~/.config/stackshot/stackshot.toml` or `$STACKSHOT_CONFIG`), and for `auto` the client's URL (`STACKSHOT_URL`, else the client's own resolution, else `[client] url`): another machine is a host that is not loopback or unspecified, not `localhost`, not this box's host name or fully qualified name, and not a bare name that is the first label of either (stackshot's `push.py` rule). When the client's setting cannot be read (no checkout and no config file), the URL rule alone decides, and no URL at all is files.
- **`SALA_INBOX_MODE=files|server`** (config; default `auto` = the client's setting; `config.example` has the line) is an override for sala alone, kept for a box that must hold in one way while its lines go the other. Any other value is read as `auto` with a line on stderr.
- **The calls** (contract interface 3 of [stackshot-contracts.md](stackshot-contracts.md)): `client.py post inbox-hold KEY… --minutes N` (both sources; a second call refreshes the time), `post inbox-release KEY…`, `get inbox-holds` and `get inbox-waiting NAME,UUID`. The keys are the session's conversation uuid and its name, as in the held files. `inbox_hold` and `inbox_touch` hold for `SALA_INBOX_HOLD_MINUTES` (10) from the last touch, after which the server drops the hold itself; **the time is never 0** (the server refuses it, a hold made by the call always ends), so a setting of 0 is sent as 1440, the longest, a negative or non-numeric one as 10, and a larger one as 1440; at most 20 keys go in a call (more are sent in several). The ledger (`salamander-inbox-holds.tsv`) and `inbox_release_stale` work as before, and `inbox_release ... wait` keeps its wait. A hold counts as made only when the answer lists every key as held in both sources.
- **`held_elsewhere`.** A release lifts only the holds the calls made. A key that another tool's file still holds (a file hold written on the server's box, a reboot's resume) is named in the answer's `held_elsewhere`, stays held, and is lifted by the tool that wrote it; sala's own hold counts as released (its ledger row goes) and one line on stderr names the keys that remain (`INBOX_ELSEWHERE` in the shell).
- **No answer is never an answer.** A server that is not reached within `SALA_INBOX_TIMEOUT` (5) s, answers 400, 401, 403 or 5xx, or answers something that is not the contract's shape is *no answer*: never "nothing waits" and never "held" (a 400 is the server's refusal of a bad key, kind or time, or its 500-key cap, not a missing call). Each call has its own timeout; after a no answer the shell does not ask again for `SALA_INBOX_BREAKER` (30) s, so a dead server costs one timeout and not one per pane.
  - **Exit code 4** of the client, its retriable delivery error (stackshot's `push.py` uses it; the inbox calls end 0 or 1, so this is defensive), is asked once more at once; a second 4 is no answer, without the 30 s pause: the next turn asks again.
  - **`inbox_line_waiting`** answers *a line waits* when it cannot be told. `sleep_ready` then refuses with "the stackshot server could not be asked whether a message waits for it", and the wake pass does not wake on it and does not count it as a failed wake: the next run asks again.
  - **`sala sleep`** is refused (nothing ended, nothing left held) when its hold call fails.
  - **A relaunch** (`revive`, `recycle`) whose hold failed goes ahead only if the pane is idle; a busy pane is left for the retry as for any other busy pane. The settle wait after a hold applies in server mode as in files mode.
  - **Releases and the orphan sweep**: a release the server did not take keeps its ledger row, so the next `inbox_release_stale` asks again. `inbox_release_orphans` (the watch's sweep for keys no ledger row names) reads `get inbox-holds` in server mode and frees only API holds (origin `api`) that carry no expiry of their own: a hold the server expires by itself is left to it, a key in another tool's file (origin `file`) is not one the calls can lift, and a reboot's resume rows are never freed. A failed list changes nothing.
- **A server or client that does not have the calls** (the client prints its usage, or the server answers 404, 405 or 501) is neither "no answer" nor a failure of the check: the hold falls back to the files when this box has the hold folder (`SALA_INBOX_HOLD_DIR`), and is no answer when it has not.
- **Tests**: `tests/inboxserver.sh` with `tests/fake-inbox-client.py` (a fake client over files that answers the final shapes and can play each failure), and server-mode cases in `tests/sleeping.sh` and `tests/sleepverbs.sh`; `tests/lib.sh` pins `SALA_INBOX_MODE=files` for every other suite.
