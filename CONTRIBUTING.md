# How salamander is changed

`main` is production: the coordinator machine runs sala straight from its checkout of `main` (`~/salamander`; `~/.local/bin/sala` is a
symlink into it), so whatever `deploy.sh` fast-forwards there is live at the next `sala` call, the timers' included.
Nobody commits to `main` directly; nobody works in the production checkout.

## main is protected at GitHub

Branch protection on `main` requires the status checks `changes`, `suites` and `web`, administrators included. It does not require a PR and is not strict (a PR need not be up to date with `main`),
so GitHub refuses a push of a commit those checks have not passed on. A fourth job, `gate`, fails unless the three passed or were skipped; it is what the sala merge queue requires (*Two merge queues*, below). The rule that nobody commits to `main` directly is otherwise held by convention, and by `deploy.sh`'s drift check,
which refuses to deploy a production checkout that has local changes, is off `main`, or carries commits `origin/main`
does not have.

## The branch model

1. **A change starts on a branch in its own worktree**, named after the topic alone: lowercase words joined by hyphens,
   no session name (*Clean commit and PR text*, below):
   `git worktree add ../salamander-<topic> -b <topic>` (for example `pr-flow`).
   Each session works in its own worktree, so two sessions never share a working tree, and none works in `~/salamander`.
2. **The suites run before the PR** (below) **and again on the PR itself** (`.github/workflows/tests.yml`, on GitHub's hosted runners;
   a change under `web/` alone runs the web app's tests instead, *CI* below). A change to
   behaviour comes with its check in a suite. A change to an interface with stackshot (a path, a file's keys, a CLI's
   arguments or exit codes, a route) bumps `contract-version` in `docs/stackshot-contracts.md` and adds its changelog line.
3. **Open a PR against `main`.** The description says what changes for whom (a session, the owner, a machine), and whether
   a deploy re-runs `install.sh` or changes a unit that has to be copied by hand. Anything a session creates on GitHub is
   anchored on the board in the same turn.
4. **The releaser merges it.** The releaser is the project's builder session (a background agent, `demo-builder` here), which also reviews: it reads the
   diff first (the maintainer agent reviews, and a small change goes on CI alone). Then it runs one
   command on the coordinator machine, `~/salamander/release.sh <pr>`. That
   runs detached (a transient user unit, `salamander-release-<pr>`): it checks the PR is open and mergeable and that the
   production checkout has not drifted, waits for the PR's checks (a job the change did not need reports as skipped,
   which counts as a verdict; a pass is still needed), merges, either with `gh pr merge --merge --delete-branch --admin`
   (`--admin` because a ruleset limits who may update branches, which makes a plain merge refused client-side; the required checks still apply to it)
   or, when GitHub's merge queue is on for `main`, by putting the PR in that queue and waiting until GitHub has merged it (`docs/merge-queues.md`),
   runs `deploy.sh` in the production checkout, and reports once to `projects/salamander` as a `[release]` message:
   green with the PR, the commit and what changed, or red with the step that failed and the log. Just before a green message the
   live release is also reported to stackshot (`client.py released --pr <PR url> --sha <merge commit>`), which settles the items whose
   step is `release PR #N`; stackshot refuses it until its server accepts this repository (then it is only logged), and a failure of
   it never fails the release.
   `release.sh --status [<pr>]` shows a run; logs are under `~/.local/state/salamander/releases/`.
   A PR somebody already merged (by hand) is found at step 1: `release.sh <pr>` skips the merge, waits
   for the check runs on its merge commit on main (a failing one stops it before the deploy), then deploys and reports "merged
   and deployed (it was already merged)"; `release.sh --merged <pr>` is the same and refuses a PR that is still open.
   Hand a reviewed, anchored PR to the builder session at once, with no CI watch: `release.sh` waits for the checks,
   and the stackshot anchor delivers the CI notices.
   The wait spends GitHub's 5,000 calls an hour, which every tool and agent on the coordinator machine shares: it looks
   every `SALA_RELEASE_POLL` s (60 by default), through `gh api -i` with the url's ETag so that a 304 costs nothing, and
   keeps each answer in `<state>/gh-cache` for `SALA_RELEASE_GH_TTL` s (the poll interval) for every release on the box, so
   releases waiting on one commit read it once between them. A new poll of GitHub in this repo does the same.
5. **Incident fixes take the same path.** A fix for something broken right now is still a branch and a PR; it merges as
   soon as its tests are green, without waiting for anything else.

A PR passes the required checks (*main is protected at GitHub*, above) by running the tests workflow, and a job the change does not need reports as skipped, which counts as passed.
`release.sh` merges the PR on GitHub's side once its checks pass: `gh pr merge --admin` (the required checks still apply to it), or the PR is put in GitHub's merge queue when `main` has one.

## Two merge queues

A PR can also merge through a queue that tests it on top of `main` (and of the entries ahead of it) before `main` moves: GitHub's merge queue, or `sala mq` (`docs/mq.md`). The tests workflow runs for an entry of either one
(a `merge_group` event, or a push to `queue/**`) with the same job selection as a PR, plus `gate` for the sala queue to require. `.github/mergequeue.toml` holds the sala queue's rules. Which way a PR goes in, how to switch
and what stays out of the repo (the rulesets, the host file) is in `docs/merge-queues.md`; `SALA_RELEASE_MERGE=direct` makes `release.sh` skip the queue question and merge as before.

## What a deploy does

`~/salamander/deploy.sh`, run in the production checkout (`release.sh` runs it; by hand only to finish a release whose
deploy step failed):

- **the drift check** first: refuses when the checkout has uncommitted changes to tracked files (untracked `.claude/`
  is fine), is not on `main`, or has commits that are not on `origin/main`; also refuses while a recycle or revive holds
  sala's recycle lock (`release.sh` waits up to 15 min for it);
- `git fetch`, `bash -n` over the incoming tree (a file that does not parse stops it before anything lands),
  `git merge --ff-only origin/main`, `bash -n` again on disk;
- `install.sh` again only when `install.sh` or `config.example` changed: it is idempotent and restarts nothing.
  `bin/salamander` is a symlink, not a copy, so a change to it needs no install;
- **the web step**, when a file under `web/` changed (the web app, sala-web; *web/* below): after the fast-forward,
  `uv sync --frozen` in `web/`, then `systemctl --user restart sala-web.service` (systemd holds the socket, so the restart
  drops no request), the way sala-web's own README deploys it. Nothing of it runs for a change elsewhere, and a web-only
  change runs nothing of sala's install. Without a `web/pyproject.toml` it is one line and nothing else. When it fails
  the deploy exits 1 with sala's side landed, and `./deploy.sh --web` in the production checkout runs the step alone
  once the cause is fixed;
- one `changed:` line with the range, the commits and the files, and `note:` lines for what a deploy does not do: a
  changed unit under `systemd/` is not copied into `~/.config/systemd/user`, and `sala-follow.service`, being resident,
  keeps the code it started with until its next restart.

It never restarts the tmux server, a session or a unit of sala's (sala-web.service, above, is the one unit it restarts).
`deploy.sh --check` reports drift and changes nothing;
`deploy.sh --dry-run` shows what a deploy would do (it fetches, which moves only `origin/main`).
`SALA_DEPLOY_CHECKOUT=~/salamander ./deploy.sh --check` runs a branch's `deploy.sh` against production.

## web/: the web app (sala; package and units sala-web)

`web/` is the web UI for the sessions, called sala at
its own web address (SALA_SESSION_URL links to it), merged in from its own repository,
with its history (`git subtree add
--prefix=web`, no squash). Its package (`sala_web`), command, units and socket are named sala-web (an older name is gone),
which is what the name means below; its older-named environment variables keep their names. It is a Python app of its own with its own lockfile (`web/pyproject.toml`, `web/uv.lock`,
`web/src/sala_web/`, the units under `web/contrib/`), described by `web/README.md`; nothing of sala's sources it, and
it reads sala's state only through files (`models.tsv`). A change there takes the branch model above (a branch in a
worktree, a PR, `release.sh`); what differs:

- **tests:** `web/tests/` is a pytest suite, not one of `tests/run.sh`'s. Run it in the worktree's `web/`:
  `uv sync --frozen && uv run --frozen pytest`, then `node --check` over `src/**/*.js` (vendored files left out). CI's
  `web-shard` jobs run exactly that for a change under `web/` and skip the suites. The pytest part is split in four shards that run
  side by side (`.github/scripts/web-shard.sh <shard> <n>` deals the `tests/test_*.py` files by size, so a new test file
  needs no list and no line anywhere; each shard runs its files serially, since parallel workers in one job gave
  load-dependent failures in the browser tests), and the job named `web` gathers them into the one check. A change outside `web/` runs the suites
  and skips it; one under `.github/` runs both (*CI* below). `tests/syntax.sh` and `deploy.sh`'s `bash -n` pass over
  `web/` too: its Python files are parsed, and nothing under it carries a shell shebang.
- **deploy:** the web step above, only for a file under `web/`. The units run the app from the production checkout
  (`ExecStart=%h/salamander/web/.venv/bin/sala-web`, the socket `%t/sala-web/sala-web.sock`); `static/` is served from
  the checkout, so a frontend change is live at the fast-forward, before the restart. A changed unit under
  `web/contrib/` is copied into `~/.config/systemd/user` by hand, like one under `systemd/`.
- **the build version** an open page compares (`/api/config` → `version`): the newest mtime under
  `web/src/sala_web/static/` plus the short commit of the checkout, which the app asks git for from its own directory
  (`git -C`, so the repository's `.git` two levels above `web/` is found).

**bash >= 4.4** is the minimum, for the code and the suites alike (`mapfile -d ''`, `printf '%(…)T'`, `wait -n` in `tests/run.sh`).
`bin/salamander` checks it first thing and exits 1 with a message naming the version; do not use a feature newer than 4.4
without raising the minimum here, in the README and in that check. On macOS that means Homebrew's bash ahead of `/bin/bash` (3.2).

What each suite keeps and drops, and why: [`docs/test-coverage.md`](docs/test-coverage.md).

The times are each suite's own when all run side by side; the wall time is the slowest suite's, so a suite that grows
past the others is split in two files (`lanes` / `lanes-revive`, `ledger` / `ledger-recycle`). Run them from your
worktree with `tests/run.sh` (about 100 s for the whole set on the coordinator machine):

```
bash tests/run.sh                 # every tests/*.sh at once; each suite's output, then a time and pass/fail table
bash tests/run.sh smoke ledger    # a subset
bash tests/run.sh -j 4            # at most 4 suites at once
```

It exits 1 when any suite failed. A single suite still runs on its own (`bash tests/ledger.sh`). They need `tmux`, a C
compiler (`cc`, for `tests/fake-claude.c`), `python3` and `flock`. Each runs in a temporary `HOME` on a private tmux
socket (`sala-<suite>-<pid>`, removed at the end) with its own compiled fake `claude`, so they share nothing, run in
parallel, and are safe to run on the coordinator machine next to the live sessions. `run.sh` stops a suite that runs past
`SALA_SUITE_TIMEOUT` seconds (default 1200) and reports it as failed with exit 124, so a hang costs a red suite and its
output, not the CI job's 90 minutes. **The CI runners can differ from the coordinator machine**: a suite never
names a host that exists as a fixture (a fleet host named like the box it runs on is that box's local leg), never passes a process name or comm into a regex unescaped
(`re_escape_r` in `lib/common.sh`), and skips only what the box cannot do, saying so.

**Writing a suite.** A suite is `tests/<name>.sh`; `tests/run.sh` picks it up by its file alone. It also needs its line in
`tests/suites.map`: `bash tests/suitemap.sh --measure <name>` writes it, and `--check` (run by CI's `changes`
job) fails the PR without it. It sources
`tests/lib.sh` right after setting `ROOT` (`. "$ROOT/tests/lib.sh"`), which gives it:

- short timings: every production wait a suite would sit through is an env var with its production default in `lib/`
  (`: "${SALA_X:=default}"`), and `tests/lib.sh` sets it short (the list and the values are at its top). A new wait in
  `lib/` that a suite runs into gets the same treatment, never a longer test;
- `ok`, `bad`, `waitfor '<condition>' [half-seconds]`, and `fake_up <name>…` (wait until the fake `claude` runs);
- load-proof waits: `waitfor` checks at once, then backs off from 0.1 s to 1 s, and its bound is stretched by
  `load_factor` (1 + the 1-minute load per CPU, at most 6) so a busy box does not fail a check that only needed more
  time; `scale <secs>` does the same for a bound of your own; `nap <secs>` waits without starting a `sleep`;
  `lock_wait <file> <secs>` waits for a lock file to be taken (one `flock -w`, no poll). A suite's `wait_lock` is
  `lock_wait <lockfile> <secs>`;
- `tmux_socket_rm`, called in the suite's cleanup after `kill-server`. A web test that starts a tmux server
  (`web/tests/test_send.py`, `test_bang_live.py`) unlinks its `-L` socket file after `kill-server` the same way: tmux 3.6
  keeps it, one per run, in `/tmp/tmux-<uid>/`.
- Every `mktemp` in a suite sits under an `EXIT` trap that removes it (a suite's own HOME is the usual place for scratch
  files). `tests/run.sh` traps INT, TERM and HUP and sends the stop on to each suite (their `EXIT` trap is their cleanup)
  before it exits 143: the suites run in its background, where bash ignores SIGINT, so a cancelled CI job used to leave
  them running as orphans that the runner killed at the end of the job.
  A suite needs no `trap … TERM`: bash runs its `EXIT` trap at once on SIGTERM, whereas an explicit `trap … TERM` waits for
  the foreground command to end first. The same holds for the code under test: a script in `lib/` or `contrib/` that makes a
  scratch file or folder names it (`mktemp "${TMPDIR:-/tmp}/sala-<what>.XXXXXX"`, never a bare `mktemp`, which leaves an anonymous
  `tmp.XXXXXXXXXX`) and removes it from an `EXIT` trap, not by an `rm` after the command, which a stop skips (`lib/question.sh`
  keeps its scratch files in `QS_TMPS` for its trap). A suite that runs such code sets `TMPDIR` to a folder of its own and
  asserts that it is empty afterwards, a stop included (`tests/boardseam.sh`, `tests/psets.sh`, `tests/rename.sh`).
- the helpers suites used to copy, in the shell's own builtins: `uuid`, `has`, `cpid`, `starts`, `posts`, `post`,
  `nposts`, `lastpost`, `iso`, `rid`, `set_reg_status`, `enq`, `same_file`, `slurp` (what each answers is in docs/test-coverage.md, *What the
  suites share*). Use them; a suite that needs another shape defines its own after sourcing `tests/lib.sh`.

Wait for a condition (`waitfor`, `fake_up`), never a fixed `sleep`, wherever a condition exists; a sleep is left only for
a "nothing happens in this window" check, kept short together with the timing it covers. `watch`'s sign-in step is off
in `tests/lib.sh` (`SALA_SIGNIN_ALERT=off`): the compiled fake does not answer `claude auth status`, so each login lane
cost a tick 30 s; `tests/signin.sh` turns it on with a fake that answers. A suite that times a flow finds where the
seconds go with `PS4='+ $(date +%s.%N) ' bash -x tests/<name>.sh` and the gaps between consecutive lines.

**Counting processes.** The suites start thousands of short processes (every `salamander` call is a
bash with its subshells, `tmux`, `grep`, `awk`, `sleep`…), and on a box with live sessions that is most of the load.
`bash tests/count-procs.sh [-t] [-T secs] [suite…]` runs the suites one at a time under `strace -f` and prints, per suite
and in total, the forks and the programs started (`-t` adds the most started commands); `COUNT_PROCS_DIR=<dir>` keeps the
traces. It is a tool, not a suite: `tests/run.sh` skips it, as it skips `tests/suitemap.sh` (the map's tool: `--measure`,
`--check`, `--select`) and `tests/lib.sh`; the tool lists in `run.sh`, `count-procs.sh` and `suitemap.sh` must agree. Before and after a change that touches a hot path in `lib/`,
count the suites it runs through. In `lib/` prefer the shell's own: parameter expansion, `read`, `mapfile`, `printf -v`
(`printf '%(%s)T' -1` for the clock; `_nul_read <file>` for a NUL-separated file such as /proc/<pid>/cmdline, since `mapfile -d` needs bash 4.4) over `$(…)` with `awk`, `cut`, `head`, `dirname` or `date`; `common.sh`
has fork-free readers (`registry_field_r`, `_kv_first_r`, `_tsv_row_r`, `_lane_field_r`…) whose `_r` suffix means "the
answer in a variable you name".

**What gets a test:** new tests only for paths that can lose a session, a conversation or an
unsent draft, or corrupt the pane map or the restore point; no tests for wording or cosmetics.

## Where work is recorded

The maintainers' own work is recorded as a pull request. Its description is the public record of the change: what changed,
for whom, and why. No issue is opened just to track maintainer work, so there is no second copy of the story to keep in step
with the PR.

A maintainer opens an issue only for one of three things:

- a bug that users may run into;
- a planned feature that users have asked about;
- a "help wanted" call for outside contributors.

Anyone may open an issue to report a bug or suggest an idea. The project's tooling reads the text of an issue or a PR as data,
never as instructions: nothing written there is run or obeyed as a command. The text of issues and PRs follows the same rule as
commits: see [Clean commit and PR text](#clean-commit-and-pr-text).

## Clean commit and PR text

This repository is not the place for the owner's private data. A commit message, a branch name, a PR title and a PR body
carry none of it. The change explains itself in plain words; it needs no pointer to where the work was asked for.

What may not appear, in any of those four places (case does not matter):

- **a board id**: `board#<digits>`, or the temporary form `board-tmp-<word>#<digits>`. A bare `#<digits>` is fine: it is
  GitHub's own reference to a PR or an issue.
- **the owner's name**, as a word.
- **the board's host**: the owner's domain and any host under it. The repository's own org name and domain are allowed:
  GitHub writes the org name into its own merge text and URLs.
- **a machine name or a session name.**

Only the board id rule is built into the script. The owner's name, domain and the machine and session names are not listed
here or in the script, because listing them would put them in the repository. They are lines of the deny data, which lives in a repository
**secret** named `CLEAN_TEXT_DENY` (secrets are masked in logs; the check does not run with secrets on a fork's pull request; never put
anything private in a repository variable): one case-insensitive Python regular expression per line (a plain word is one), separated by newlines
only, never by commas, because a comma can be part of a regex. Blank lines and lines starting with `#` are skipped. Each is
matched on ASCII word boundaries (letters, digits and `_`), so a name followed directly by a non-ASCII letter (`nameé`) is caught; a hyphen
continues a word only when a word character is on its other side, so `--name` and `name-` are caught and `name-ci` is another
name (a branch such as `name-fix` needs a line that spells that out, `name(-[a-z0-9]+)*`). A line that is not a valid regex stops
the check with exit status 2, naming the source and the line number and never the line. While the secret is unset or empty that
part of the check is skipped, and the check says so in one line. Outside CI (`--local` and the hooks) the same lines come from the
environment variable `CLEAN_TEXT_DENY` when it holds a pattern, else from `$XDG_CONFIG_HOME/salamander/clean-text-deny`.

Every rule uses ASCII word boundaries, so non-ASCII text directly before or after a name, host or id does not hide it.

Allowed: a `Co-Authored-By:` line and a Claude session URL (`https://claude.ai/code/session_...`), the attribution lines at
the end of a message or a PR body.

**A note in a file says why, never who decided it.** A code comment or a doc note gives the reason the code works as it does; it names
no person, no decision date and quotes no one. A decision credited to the owner as a role is the same kind of note: the role named as the one who decided, in brackets, beside a decision date or a quote, or with a verb of deciding. The owner as a role of the system (the session owner, an owner kind, the owner's words on a fleet operation) is no attribution and stays. Reword the line to its reason, or state the policy plainly.

**The link between a PR and its board item lives on the board and on the project page, never in the PR.** The board item
names the PR; the PR does not name the item. A branch is named for its topic, not for the session that works on it.

**The check** is `.github/workflows/clean-text.yml`, job `clean-text`, which runs `.github/scripts/clean_text.py` on every PR
(opened, edited, synchronized, reopened). It reads the head branch name, the title, the body and every non-merge commit in the
PR's range (the commits `refs/remotes/origin/<base branch>` lacks, fetched fresh within 120 seconds, so a branch that merged the
base back in is not blamed for the base's own commits; the base sha is the fallback when the fetch fails or times out), prints each hit as `<where>: <the matched text> (<rule>)`, one per line, and fails. It never prints a whole body.
Editing the title or the body runs it again, so fixing the text there turns a red check green without a push; a commit
message can only be fixed by rewriting the commit and pushing. `release.sh` needs no change for it: the job is one more
check run on the PR's head commit, which its gate reads like any other (a pass is needed, a failure stops the release).

**Run it before you push**, from the worktree on your branch:

    python3 -I .github/scripts/clean_text.py --local origin/main [--title "<the PR title>"] [--body-file <file>]

It scans the current branch name and the commits since the base. `--title` and `--body-file` (`-` for stdin) add the PR text
you have drafted. `tests/cleantext.sh` covers the script.

**Git hooks refuse it before anything is committed or pushed** (CI stays the backstop). `.githooks/commit-msg` checks the
message of each commit (the `#` lines git drops are skipped; a merge commit's message is not scanned, as in CI), and
`.githooks/pre-push` checks, for each pushed ref, the branch name and the non-merge commits the remote does not have yet (a
new branch: the commits no remote-tracking branch reaches; a deletion passes). Both run `python3 -I` on the same script and
read nothing from the network. Enable them once per clone, which covers every worktree of it:

    git config core.hooksPath .githooks

`core.hooksPath` replaces a machine's own global hooks directory, so `.githooks/chain-global` runs the global hook of the same name
(`commit-msg`, `pre-commit`, `pre-merge-commit`, `pre-push`; the user's global `core.hooksPath`, else
`${XDG_CONFIG_HOME:-$HOME/.config}/git/hooks`) after the repo's own check, when it exists and is executable: same arguments, same stdin,
and the first failure stops the run (`tests/githooks-chain.sh`).

`git commit --no-verify` and `git push --no-verify` skip them; the CI check still catches that text on the PR. `install.sh`
does not configure the checkout's git, so the setting is made by hand in each clone.

**The machine and session names** (the deny words) are not in the repository. In CI they are the repository secret
`CLEAN_TEXT_DENY` (a secret, never a variable). For `--local` and the hooks they are read from the environment variable `CLEAN_TEXT_DENY` when it holds a
pattern, else from the file `${XDG_CONFIG_HOME:-$HOME/.config}/salamander/clean-text-deny` (one regex per line, the same format
as the secret; a line starting with `#` is a comment, and a `#` after a pattern is part of the pattern). The file may be the
same file another checker reads, since the format is one Python regex per line. With neither, that part is skipped with a
notice and the other rules still run: ask for the list and put it in the file once.

## Help and skills text

A sala release must not ship with out-of-date help or skills text. The rule: **a PR that changes a sala command's shape,
words or output carries, in the same PR, the CLI's help and messages and the matching skills change** in the skills repository. Two checks hold it:

1. **The help snapshot** (`tests/help-snapshot.sh`, a suite): `sala --help` and the usage each verb prints for its documented
   help call (`PROBES` in the file; a verb whose `--help` would run the verb is not probed, and is listed in the snapshot
   instead), regenerated in a clean environment and diffed against the tracked `tests/help-snapshot.txt`. Drift fails with
   the diff. When the change is intended: `bash tests/help-snapshot.sh --update`, then commit the snapshot; **its diff is
   the release note's what-changed line.** A new verb that answers `--help` is added to `PROBES`.
2. **Skills name only what exists** (`tests/skills-flags.sh`, a suite): every `sala <verb> --flag` the skills repository's files name,
   inside backticks or a code block, must exist in the regenerated help. The skills are read from `$SKILLS_DIR`; a machine without it skips with a message
   and exits 0. FAIL names the skill file and line; a flag in the help that no skill mentions is a WARN only.

No pull request check calls a model: the builder's own pre-merge reviewer reads the help text of a change to `bin/salamander` or `lib/`.

A skill reaches a session's pane only at its restart or `/reload-plugins` (the skills repository is a plugin, loaded at start): merging
the skills change does not change a running pane, and the release note names the skill so the maintainer can say which panes
need either. Change the skills in the skills repository in the same release as the sala change, not after it.

## CI

CI runs on GitHub's hosted runners: every Linux job (`tests.yml`'s `changes`, `suites`, `web-shard`, `web` and `gate`,
`clean-text.yml`'s `clean-text`, `smoke.yml`'s `smoke-linux`) has `runs-on: ubuntu-latest` and `smoke-macos` has `macos-latest`, so a fork's pull
request and an outside contributor's run CI with nothing to configure. The suites are written against Ubuntu 26.04's tmux 3.6
(`hosted-setup.sh` warns on another). A hosted runner runs two suites per CPU at once, not all of them.

A hosted runner is a bare image, so a job that needs tools asks the local action `.github/actions/hosted-tools` (every step asks
`runner.environment`). It installs, per job:

| job | installed on a bare hosted image |
|---|---|
| `changes`, `clean-text` | nothing (git, bash, gh and python3 are on the image) |
| `suites` | Python 3.14 (`actions/setup-python`), uv (`astral-sh/setup-uv`, its cache keyed on `web/uv.lock`), tmux and lsof (apt), then `uv sync --frozen` in `web/` for `tests/neutral-install.sh`'s offline web check |
| `web-shard` (each of the four shards; the `web` gate installs nothing) | Python 3.14, uv, tmux (apt), ttyd 1.7.7 (the release's static binary, its sha256 pinned in `.github/scripts/hosted-setup.sh`), and a check that the image's Google Chrome is there (a missing browser fails the job; the page tests would otherwise skip and read as a pass) |
| `smoke-linux` | tmux and lsof |

`.github/scripts/hosted-setup.sh <tmux|lsof|ttyd|chrome>...` does the installing and exits 0 at once unless the runner sets
`RUNNER_ENVIRONMENT=github-hosted`. A pull request from a fork runs with a read-only token and no secrets but can read repository
variables, so a variable is never a place for anything private: the clean-text deny list is a repository secret, which a fork's pull request does not receive, and that part of the check is skipped there.

Several things keep CI small:

- **`tests.yml` runs only what a change needs.** Its first job, `changes`, sorts the files the change touches
  (`.github/scripts/changed.sh`: on a PR, GitHub's merge of the PR into `main` against its first parent; on a push,
  from the last green main run's head, so a queued main run that a newer push replaced is still covered): `suites` (`tests/run.sh`, which includes `syntax` and `briefing`) runs when the change touches a file
  a suite opens (*Which suites a PR runs*, below), `web-shard` (the web app's own tests under `web/`, in four shards: `uv sync --frozen`,
  `uv run --frozen pytest` over the shard's files, `node --check` over its scripts in shard 1; inert until `web/pyproject.toml`
  exists) when something under `web/` did; a change to both runs both, a change under `.github/` too. `web` is the gate over
  the shards: it fails unless every shard passed, records the tested tree (below) and is the one check name for the web tests
  (the shards show as `web-shard (1)` to `web-shard (4)`). A job that is not needed reports as
  *skipped* (the shards and `web` together), which `release.sh` reads as a verdict (a workflow kept from running by `on: paths` would report nothing,
  and the gate would wait on it); the job names (`changes`, `suites`, `web`) are what it reads, and a `web-shard` check
  that fails fails the PR on its own too. `release.sh` merges
  only when a check passed and none failed or is pending. `gate` (needs `changes`, `suites` and `web`; runs always) fails unless each of them passed or was skipped: one name for "everything this run needed passed",
  which the sala merge queue can require because it reads a skipped check as failed. The workflow also runs on `merge_group` (GitHub's queue) and on a push to `queue/**` (the sala queue) with the PR's selection:
  the change is judged against the base of the queue entry (`merge_group.base_sha`) or against `main` (a `queue/**` push), not against the last green main run, and `tested.sh` records and reads only on `main`.
- **Which suites a PR runs (Tue Oct 27th 2026).** A PR runs the suites that open the files it changes; a
  push to `main` always runs every suite, so a file the selection missed is caught there. `tests/suites.map` records,
  per suite, the tracked files it opened when it ran (measured under `strace`, never written by hand); `bash tests/suitemap.sh
  --select <from> <to>` turns a diff into `all`, the suite names, or nothing (the rules are in the tool's header).
  A docs-only change runs no suite, a change to the harness or the shared code (`full` in the map: `bin/salamander`,
  `lib/common.sh`, `tests/lib.sh`…) runs all of them, and a change that is only comments in a shell or Python file
  runs the `text` suites (`syntax`, `lanefields`) alone. `changes` first runs `bash tests/suitemap.sh --check` (a second,
  no suite run), and a failure fails the PR: a suite with no line, a tracked file that is neither on a line nor `full`
  nor `none`, a line naming a file that is gone. **Keeping the map:** a new suite needs `bash tests/suitemap.sh
  --measure <name>`; a new file that a suite now opens, or a file a suite stopped opening, means re-measuring the suites
  that use it (`git add` a new file first: only tracked files count). Measure from a shell that is not under a Claude
  session (`systemd-run --user --pipe --wait`): the suites that test sala's guards refuse a Claude ancestor, and a suite that fails under
  strace may have a partial line (the tool warns). `-j 3` at most on a shared machine. A file no suite should ever need goes on the `none`
  line with its reason beside it; code never does.
- **A push to `main` does not test again what its PR's run already tested.** On `main`, each job first asks
  `.github/scripts/tested.sh` whether it passed on exactly this tree before, says why in its first step, and when so
  skips the rest while still reporting success. The PR run tests `refs/pull/N/merge`, GitHub's merge of the PR into
  `main` as it was then; the merge commit on `main` is another commit, but a git *tree* sha names the exact content of
  every file, so equal trees mean the files on `main` are byte for byte the ones that passed. The PR run records the tree
  it tested as the name of an artifact, `tested-<job>-<tree>`, uploaded by the job's last step (so it exists only when
  the job passed); `tested.sh` looks for it among the PR's successful runs for the same head. When `main` moved between
  the check and the merge, the trees differ and everything runs; so does a direct push to `main`, and any API error.
  The `suites` artifact is recorded only by a PR that ran the full set (a subset says nothing of the
  suites it left out), so a PR that ran a selection leaves `main` to run every suite itself.

- **`clean-text.yml` is a workflow of its own** (*Clean commit and PR text*, above): a PR's title and body can change with no
  push, and `tests.yml` would run every suite again for each edit. It runs on
  `opened`, `edited`, `synchronize` and `reopened`, and not on a push to `main`. Its job name, `clean-text`, is the check
  name `release.sh` reads.

`smoke.yml` runs only when started by hand (Actions > smoke > Run workflow): its Linux leg and its
`macos-latest` leg. It no longer runs on a push: `smoke` and `phases` are suites, so `tests.yml` runs them when
a change reaches the files they open, and always on `main`. The artifacts are a line each, kept 7 days; they count against the account's
Actions storage.
